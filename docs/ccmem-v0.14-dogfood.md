## 二、W4：唯一有连续生产读数的一条 —— 并且它当场抓到一个生产问题

**数据源**：`~/.claude/ccmem/daemon-cost.jsonl`，**265 行，0 行解析失败**。
窗口 `2026-08-29 19:33` → `2026-09-04 00:17`，跨 **5.20 天**。

### 2.1 它确实答出了 P1#5 的第 2、3 个数（这是 W4 的验收判据）

| 问题 | 读数 |
|---|---|
| **token 用量** | `input` 合计 **454**、`output` 合计 **309,517**（178 行有值） |
| **稳态周成本** | 窗口内合计 **$59.44**（178 行有值）⇒ 折算 **≈ $80.06 / 周** |

⚠️ **$80/周 这个折算值的效力边界**：窗口只有 5.2 天、且横跨了本仓库自己的高强度开发期（W3 实现与 review 都在窗口内），
**不能当作长期稳态**。它是"当前这种使用强度下的量级"，不是常数。

### 2.2 🔴 W4 抓到的生产问题：`summarize_pending` 有三分之一在超时

| | n | 占比 |
|---|---|---|
| `summarize_pending`（JSON 路径） | 261 | — |
| **其中 `timed_out: true`** | **83** | **31.8%** |
| `security_audit`（text 路径） | 4 | — |

**超时那群的 `wall_clock_ms` 是 min `59,939` / 中位 `60,013`** —— 紧贴 `config.default.json` 的
`llm.claude_p_timeout_per_task.summarize_pending = 60000`。未超时那群是 min `10,968` / 中位 `32,415` / max `60,609`。
⇒ **不是偶发抖动，是一半以上的调用本来就贴着 60s 上限在跑。**

**逐日超时/总数**：`08-29 0/1` ｜ `09-01 2/70` ｜ `09-02 15/48` ｜ **`09-03 65/137`（47%）** ｜ `09-04 1/9`。
⇒ *** **超时率在窗口内显著上升，09-03 已接近一半。** ***

🔴 **这条只有 W4 落地之后才看得见** —— 超时路径 `exit_code` 记为 `null`、`total_cost_usd` 记为 `null`，
任务本身不报错、audit 行也照写。**这正是 W4 存在的理由**，也是本轮 dogfood 最值钱的一条。
⚠️ **本轮不修**：定超时值、切工作、还是降频，是设计决定。**列入 v0.15 输入（§八）。**

### 2.3 spec 里担心过、而数据判掉了的一条

§二 W4 要求把**排队时间**与 spawn→close 分开记，理由是 `callClaudeP` 经 `tail` promise 链串行化、排队可以任意长。
两个都记了，实测：`queue_wait_ms` **p50 `0` / p90 `1` / max `13`**，而 `wall_clock_ms` p50 `41,296` / p90 `61,164`。
⇒ **排队时间在这个负载下可忽略。担心是对的，但量级不成立。**（`wall_clock_ms` max `1,008,354` = 16.8 分钟，
是唯一一条离群，且它同时被标了 `timed_out` —— 单条离群，本文档不解释它，只如实记下。）

### 2.4 text 路径的 `null` 纪律在生产里成立

4 次 `security_audit` 走 text 路径，**4 次的 `total_cost_usd` 全为 `null`**，没有一次被估算成 `0`。
spec §五 5.2 W4 那条测试钉的就是这件事，**生产读数与它一致**。

## 三、W3：干跑（唯一一次拿真实库量误伤的机会）

**方法**：`sqlite3 ".backup"` 出一致性副本（**不是 `cp -r`** —— 活的 WAL 库 + 常驻 daemon，`cp -r` 可能拿到撕裂快照），
在副本上重放各阶段的扫描器。副本由控制器准备，实现者手里不给生产路径。

### 3.1 干跑推翻了改强的第一版

在 **9,945 条** active/probation 记忆上：**第一版改强会隔离 10 条合法记忆，且全是同一形状 —— 安全约定**
（"不要把密钥放进仓库/argv/提交信息"这一类）。逐阶段归因：**窗口放宽 7 条、中文模式 3 条**。
⇒ **32 条语料完全看不见这个形状**：语料里根本没有"安全策略陈述"这个类。

**处置**：窗口收回 `.{0,80}`；中文凭证模式去掉 `token`（中文技术写作里它压倒性指 LLM token —— 词表错误，不是调参）；
中文绕过模式去掉 `校验`。并把四种真实形状补进语料的新类 `benign_policy`。

**收窄后实测**：真实库 9,945 条上，改强后会隔离的与改强前**完全相同 —— 新增 0、丢失 0**。
⇒ *** **必须如实说：W3 对这个库【当下】的可测效果是零。** *** 它的价值是前瞻性的。

### 3.2 语料读数（`npm run threat:report`，不进 CI）

benign false positives **0/18**；missed attacks **7/19**；delta vs baseline **SAME 37 / FIXED 0 / BROKEN 0**。
跑完 `git status --porcelain` 无输出 —— **报告脚本绝不写回**，只有 `-- --accept` 才写。

### 3.3 干跑顺带撞到的两个 `secretScan` 缺陷（都不在 W3 范围内）

1. **`openai_key` 缺词边界** —— `/sk-[A-Za-z0-9_-]{10,}/` 把 `task-completion` 里的 `sk-completion` 判成 openai key，
   **干跑实测命中一条真实记忆**。✅ **2026-09-04 已修**（加 `\b`，严格收窄），并补了正反两条回归测试
   —— 在此之前 `secretScan` **全仓库零测试**。
2. 🔴 **`credential_assignment` 从 v0.4 起就是死的，至今未修**。源码里那两个本应是 `\b` 的位置
   **是字面 0x08 退格字节**，于是正则要求内容里真的含退格符 ⇒ **永远不可能命中**。
   引入于 `3400ba6 feat: implement v0.4 diagnostics and revalidation flows`（2026-06-06），
   **三个月无人发现，因为终端、`grep`、`sed` 都会把 0x08 吃掉，肉眼看它完全正确**。
   ⚠️ **刻意不照原样修**：在副本的 **3,251 条 global scope active 行**上干跑，修好后**新命中 5 条、
   5 条全落在自动隔离档**（trust<0.6 且未 pin），而**触发词是 `secret metadata` / `token cap` /
   `token accounting` / `token budgets` / `token cost and context` —— 5 条全是误伤，真凭证 0 条**。
   与 §3.1 那条"token 在技术写作里指 LLM token"同型。**照原样修 = 让扫描器隔离 5 条合法记忆。**
   ⇒ 要修得先收窄词表，**那是设计决定**，列入 v0.15 输入。

## 四、W0 / W1 / W2：默认关，因此生产里没有行为可观测

- **本机 `~/.claude/ccmem/config.json` 只有 `embedding` 一段**（顶层键就这一个），**没有 `security`、没有 `eval`**。
  ⇒ W1 的 `quarantine_all_sources_at_write` 与 W2 的 `disable_scope_isolation` **都取默认 `false`**，
  两条工作流在生产里**行为零变化 —— 这符合设计**。
- ⇒ 同时也意味着：**生效的 `security.*` 全部来自 `scripts/lib/config.mjs` 的 `DEFAULT_CONFIG`，
  而不是 `config.default.json`**。这一条对 W0 的读法很要紧：`config.default.json` 是给新用户拷的模板，
  **没有 `config.json` 的进程读的是代码里的常量**。
  ✅ 2026-09-04 已为 `scan_patterns_version` 这一个键加了两份配置源的相等断言（漂移当场变红）。
- **W0 只在人主动跑 `ccmem admin diagnose` 时执行** ⇒ 它**没有被动运行证据**，本文档不给它编造一条。
  ⚠️ 且要记住：默认 `diagnose` 输出**只有计数、不含键名**，键名只在 `--config` 下出现。

## 五、🔴 dogfood 撞见的一条结构事实：**改代码不需要合并就已经上线**

不是 v0.14 的内容，但它决定了本仓库所有 dogfood 的读法：

| 实测 | 结果 |
|---|---|
| `~/.claude/plugins/ccmem` 是什么 | **符号链接 → `/Users/biran/code/skills/ccmem`（工作树本身）** |
| 三个钩子怎么跑 | `hooks/hooks.json`：`node …"${CLAUDE_PLUGIN_ROOT}/scripts/hook.mjs" <phase>`，**各自都是新进程** |
| launchd daemon 跑哪份 | plist `ProgramArguments` 末项 = 同一棵树的 `scripts/daemon/main.mjs` |

⇒ **钩子每次调用都重新 `import` 当前 checkout 的代码 ⇒ 生效闸门是 checkout，不是 merge。**
⇒ **唯一例外是常驻 daemon**：它在进程启动时把模块读进内存。实测那个进程起于 `2026-09-01 20:53:35`，
而改强后的 `scripts/lib/threat-scan.mjs` mtime 是 `2026-09-03 11:34`
⇒ **W3 合并当天，写入路径上跑的是新扫描器、后台排水路径跑的还是旧的。**

📌 **对 dogfood 的直接后果**：任何"这条改动还没上线"的说法，在本仓库都要先验证一遍。

## 六、revalidation 排水的真实速率（决定了 `scan_patterns_version` 该不该 bump）

读 `audit_log` 的 `revalidation_audit_run`：**90 次**，窗口 `2026-06-07 02:17` → `2026-09-03 02:19`；
`daily` **87 次 × 100 行**（`batch_size` 默认 100），`lazy` 三个月**总共只跑过 3 次**（286 行 —— 它有天级 lease）。
每次耗时 **24–144ms**。⇒ **排水速率 100 行/天。**

副本上的库形状：总 `10,389`；active/probation **`9,945`**；已隔离 `3`；
**已盖 `2026.07` 的 `6,152` 行、从没扫过（`NULL`）的 `4,237` 行**；
待扫集合里落在「可直接隔离」侧（trust<0.6 且未 pin）的 **`9,666`** 行（另 `279` 条只会被 flag）。

⇒ **bump 版本号的增量工作 = 把那 6,152 行再扫一遍，而 §3.1 已证明新旧扫描器在这个库上判定完全相同**
⇒ **0 个判定变化，代价约 61 天额外排水 + 一次必须的 daemon 重启。**
**人 2026-09-03 据此裁决：不 bump。**

📌 历史对照：**88 天排水期间 `revalidation_quarantine_in` 总共只发生过 2 次。**

## 七、本文档没能验证的

1. **W0 的被动运行证据** —— 它只在人跑命令时执行，没有旁证可取（§四）。
2. **W1/W2 开关打开之后的行为** —— 需要打开开关跑评测，那属于 paper 仓库的 harness，且开关一开就会
   写别的项目的记忆（W2 的持久性风险，spec §六 风险 2）。**本文档不为此打开任何开关。**
3. **W3 的前瞻性价值** —— 它关掉的四类绕过恰好不出现在当前 9,945 条里，**所以"有没有用"这件事
   在这个库上不可观测**。语料是它唯一的度量。
4. **超时率上升的根因**（§2.2）—— 只有计数，没有归因。
