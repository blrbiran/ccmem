# Finding 15 —— 带外嵌入延迟探针（设计）

> 2026-08-04。目标是让 `openai_timeout_ms` **有实测依据可重新推导**，而不是再换一个拍脑袋的常数。
> 本文档只写设计与其证据。实现计划另出。

## 〇、为什么需要一个探针（问题陈述）

`openai_timeout_ms: 800` 是 Finding 4 为 hook 路径选的，当时 hook 内部预算 200ms、"反正会降级"。
V8 / Finding 13 之后 harness 给到 5s、内部预算给到 2000ms，**而这个常数从未被重新推导**。

Finding 15 已取证它"落在延迟分布中间"。本轮把这句话量化了：

⚠️ **下表全部取自同一个冻结快照**（`metrics.jsonl` 于 2026-08-04 21:32 复制出的副本）。
`metrics.jsonl` 是活文件，会在分析过程中被追加 —— 本文档初稿就因为跨查询取数而出现过
"总数 160 / 161、`B-fail` 43 / 44"的差一不一致。**任何要放进文档的计数都必须来自单一快照。**

| 量 | 值 | 来源 |
|---|---|---|
| 窗口 | 2026-08-02 11:12 → 08-04 21:32 | 熔断修复（`fc66890`）之后，避免与旧 regime 混算 |
| `prompt_submit` 行数 | 193 | 快照 |
| `A`（语义成功） | 130（其中 **25 次是查询向量缓存命中**，`embedMs = 0`） | |
| `B-fail` | **54**，全部 `Request timed out.` | |
| `B-circuit` | 8 | |
| `B-off` | 1 | |
| **真实 embed 尝试** | 105 成功 + 54 超时 = **159** | 排除 25 次缓存命中 |
| **截尾率** | **54/159 = 34.0%** | |
| 丢掉语义通道 | 63/193 = **32.6%** | 与 Finding 15 原文的"约 1/3"一致，样本更大 |

> **结论：800ms 大约就是真实查询嵌入延迟分布的第 66 百分位。**
> 成功样本（n=105，min 322 / p50 669 / p90 736，**超过 800ms 的只有 1 条**，即 §八 那条未解释的 948ms）
> 是**被 800ms 条件筛选过**的分布，它算不出 p99 ——
> 真正的 p99 整个落在截尾区里。这正是 Finding 15 说"要么临时放大超时取样、
> 要么用回填侧无截断样本近似"的原因，也是本探针存在的理由。

### 附带确认的两件事

**1. `maxRetries: 0` 已经生效，截尾点是干净的。**
`openai.mjs:25` 的 `maxRetries: 0` 于 2026-08-02 00:47（`9c46632`）落地，早于本窗口。
所以 `B-fail` 簇的 802–808ms 是**单次尝试**撞上 800ms 上限，不是重试的倍数。
（`openai.mjs:20` 注释里那句"800 实测到 1683ms 墙钟"描述的是**修复前**的状态，别读成现状。）

**2. dogfood 里有一条已过期的断言，需要改。**
`docs/ccmem-v0.13-dogfood.md:725` 写「修复后 6 次失败、零次熔断」。
该句在落笔时（08-02 12:20）为真，**当晚即被证伪**：熔断在 08-02 **23:10:20–23:20:13 之间开了 7 次**，
**并在 2026-08-04 21:01:41 又开了第 8 次 —— 就发生在本设计成文的当天。**
已记 `bug-062`，修正随本轮一并落地。

> 这条不只是文档陈旧。它是**这个问题至今仍在持续产生**的直接证据：
> `openai_timeout_ms: 800` 每天制造约三分之一的超时，这些超时持续喂给熔断器的连续失败计数。

触发链已完整还原，并揭示一个值得单独记住的机制：

```
22:55:51  B-fail          失败 1
22:57:29  B-fail          失败 2
23:07:35  A  (embedMs=0)  ← 查询向量缓存命中，未触碰 provider，因此不重置失败计数
23:08:57  B-fail          失败 3
23:10:20  B-circuit       闸门打开
```

> **缓存命中不重置连续失败计数。** 统计"连续"类计数器时，只有真正触达 provider 的调用才算数；
> metrics 里的成功行并不等价。Finding 14 的"连续 3 次"语义工作正常，喂给它的正是 Finding 15 的超时。

## 一、这个决策的硬约束（先于取值）

超时不能只看延迟分布，因为**超时之后还要跑 lexical 回落**，两段之和必须留在 hook 预算内。
超出预算时 `withHookSafety` 的 `Promise.race` 会掐断整个 hook 并**返回空上下文** ——
那比今天的 lexical 回落**更差**。

| 层 | 值 | 出处 |
|---|---|---|
| harness `UserPromptSubmit` | 5000ms | `hooks/hooks.json:21` |
| hook 内部预算 `prompt_submit` | **2000ms** | `hook-safety.mjs:21` |
| embed 之外的成本（A 路径，n=105） | p50 195 / p90 259 / p99 327 / max **422** | 快照实测 |
| lexical 回落成本（B-fail，n=54） | p50 184 / p90 232 / max **638** | 快照实测 |
| `ms_total`（n=193） | p50 867 / p99 1138 / max 1441 | 快照实测 |

```
embed_timeout + 回落成本(实测 max 638) < 2000ms   ⇒   embed_timeout ≲ 1360ms
```

> **所以真正待答的问题不是"p99 是多少"，而是"把超时从 800 抬到 ~1300 能捞回那 54 次里的几次"。**
> 若卡顿是 850–1200ms 量级，抬上去能捞回大半；若是 10s 量级的挂死，抬上去一次也捞不回、
> 只会让每次失败多烧 500ms。**这个答案完全藏在截尾区里，只能靠取样得到。**

## 二、方案选择与人类裁决

取样方式属人类裁决（Finding 15 原文即如此规定，因为取样动作会改变生产行为）。
2026-08-04 的裁决与理由：

| # | 裁决 | 理由 |
|---|---|---|
| 1 | **daemon 侧带外探针**，不临时放大线上超时 | hook 路径行为零变更；临时放大只是把截尾点从 800 搬到 1300，仍然截尾 |
| 2 | **常驻仪器，速率可配**，非一次性战役 | 修完要用同一把尺子验证超时率真的降了；日后漂移也能被看见 |
| 3 | **取本地记忆库的真实文本** | 回填本就在把这些内容发给同一个 provider，**不新增任何外发面** |
| 4 | **默认关，本机显式开** | 它会定期发真实 API 请求，影响的不只本机；不替别人做这个决定 |
| 5 | **顺手记 `prompt_chars`** | 真实 prompt 长度分布至今无记录，这是唯一能让取样长度日后被校准的办法 |

被否掉的方案与原因：**临时放大线上超时**（仍截尾、且失败者每次多烧 500ms）；
**借回填侧样本近似**（batch ≤100 与单查询不可比）；**不取样直接按预算上限定值**
（违背 Finding 15 自己定的"判据是实测"）。

## 三、架构

新 daemon 任务 `embed_latency_probe`：

```
scripts/daemon/tasks/embed-latency-probe.mjs   ← runEmbedLatencyProbe(db, task)
scripts/daemon/dispatch.mjs                    ← 注册（既有 if 链）
scripts/daemon/loop.mjs                        ← 调度
```

### 3.1 调度：不走 lease，用 loop 内的模块级时间戳

**这是对仓库惯例的一次有意偏离，按 Rule 11 明说而不是闷着改。**

现有八个任务都用 `tryClaimLease(db, type, dateKey, ranBy)` 去重。
lease 的价值是**跨进程幂等**（daemon / opportunistic / manual 可能抢同一周期）。
探针只由 daemon 发起，而 daemon 锁只允许一个进程 —— **这个价值对它恒为零**，
所以不走 lease。**理由只有这一条。**

> ⚠️ **本节初稿的理由是错的，改正记录在此。** 初稿写「全仓库没有任何地方清理 `task_runs`，
> 5 分钟一次的探针会变成 288 行/天、无上限」。**`task_runs` 是被清理的**：
> `tier15.mjs:62` 与 `:130` 两处都执行 `DELETE FROM task_runs WHERE date_key < dayKeyDaysAgo(30)`。
> lease 的代价因此**有界**（30 天约 8.6k 行），是「白付」而不是「无限累积」。

**真正无界的增长在另一张表，必须写明：** 每次探针都会往 `tasks` 插一行，
而 `scripts/` 下**不存在任何 `DELETE FROM tasks`**。`interval_ms = 300000` 时约 **288 行/天、10.5 万行/年**，
且 `tasks` 只有 `uniq_tasks_summarize_session_seq` 一个索引 —— 没有 `(status, scheduled_for)` 索引，
所以 `mainLoop` 的到期查询（`loop.mjs:342`）是在一张只增不减的表上全表扫描。

> **本轮只披露，不修。** 给 `tasks` 加保留策略是全仓库级的决定，
> 不该由一个探针顺手做掉；但把它藏起来同样不可接受 —— 开启探针的人有权知道这笔账。

因此：`loop.mjs` 里持一个模块级 `lastProbeAtMs`，`nowMs - lastProbeAtMs >= interval_ms` 时入队。
daemon 重启会重置它 —— 后果只是重启后立刻探一次，可接受。

### 3.2 实际节奏会不规则，这是采样节奏不是被测量

loop 空闲时睡 **300s**、活跃时睡 30s（`loop.mjs:322`）。
所以 `interval_ms = 300000` 实际落在 **5–10 分钟之间**。

> **这不影响分布效度**（每个样本仍是一次独立的完整测量），但**必须写明**，
> 否则下一个人会把节奏不齐当成数据丢失去排查。

### 3.3 并发：不存在竞态（已验证）

`loop.mjs:326-331` 是 `for (const task of due) { await runTask(...) }` —— **任务严格串行**。
所以探针（10s 超时）与 `vec_backfill`（45s 超时）**不会并发**，
`openai.mjs` 的模块级 client 单例不会被对方换掉。交替运行时各自重建一次 client，
代价仅为对象构造（无 import），无正确性问题。

## 四、配置（默认关）

```jsonc
"embedding": {
  "latency_probe": {
    "enabled": false,            // ← 严格 === true 才开
    "interval_ms": 300000,
    "timeout_ms": 10000,
    "file": "embed-latency-probe.jsonl"
  }
}
```

⚠️ **一条容易读反的不对称，作为显式决定记录在此**：
本开关用 **`enabled === true` 才开**（缺省关）；
而相邻的 `recordDecisionMetric`（`metrics.mjs:60-64`）是 **`enabled === false` 才关**（缺省开）。
两者语义方向相反且字段同名。这不是笔误：决策数据的缺省必须是"记录"，
探针的缺省必须是"不发请求"。**改动任一处前先读这一段。**

`interval_ms` 是下限而非精确周期，见 §3.2。

## 五、探针本体与隔离

```
1. 取文本： SELECT content FROM memories ORDER BY RANDOM() LIMIT 1，按 hook 同规则截 2000 字符
2. 构造隔离配置： { ...cfg.embedding, openai_timeout_ms: timeout_ms, api_timeout_ms: timeout_ms }
3. t0 = Date.now(); try { await provider.embed([text], 隔离配置) } catch (e) { err = e.message }
4. ms = Date.now() - t0
5. 丢弃向量，落一行
```

### 5.1 四条隔离，一条都不能少

| 隔离 | 不做会怎样 |
|---|---|
| **不调 `recordEmbedFailure` / `recordEmbedSuccess`** | 探针自己的超时会去开**真实检索**的熔断闸门 —— 用测量工具制造被测现象 |
| **不写 `query_embedding_cache`** | 污染 hook 的缓存与命中率，而缓存命中正是 §〇 里那条"不重置失败计数"的关键变量 |
| **不预检熔断状态** | 闸门开着的时候**恰恰最需要数据**；预检会让探针在最该采样时沉默 |
| **丢弃向量** | 探针的产物是延迟，不是向量；写回任何地方都越界 |

> §六 的隔离测试守的就是这一节。**它必须被亲眼看着变红。**

### 5.2 行结构

```json
{ "ts": 0, "ms": 0, "ok": true, "error": null,
  "timed_out_at_probe_limit": false, "text_chars": 0, "signature": "provider:model:dim" }
```

- **`timed_out_at_probe_limit`** —— 探针自己那 10s 也被撞到时为 `true`。
  **二次截尾必须可见**，不能塌缩成一个普通的"失败"，否则本探针会重演它要解决的那个问题。
- **`signature`** —— 换模型后两段分布不得被静默混算。项目已有这个签名概念（人类裁决 2：换模型检测器整体移除，因为签名机制已正确覆盖）。

### 5.3 落盘政策：永不轮转、永不限容

沿用决策数据的政策与理由（`metrics.mjs:44-51`）：`recent_injections` 的 14 天保留
**曾把这个决策需要的数据毁掉过一次**，那正是 v0.13 推迟 L2.5 阈值的原因。本探针的产出同属决策数据。

文件大小由 `diagnose --feedback` 与 `l25-probe.jsonl` **并列打印** ——
与人类裁决第 6 条一致：**刻意让运行时成本可见，不要"优化"掉**。

## 六、错误处理

- **探针失败永不让任务失败。** 失败正是要采集的样本；让任务失败会触发重试风暴。
- **provider 不是 openai、或无 key ⇒ 不跑、不记行。** 本探针只测 openai 路径。
- 配置中途关掉 ⇒ 停止入队，无需清理。

## 八、已知局限（不得省略）

1. **daemon 常驻、hook 每次冷启。** `embedMs` 含 `load()` 的动态 import 与 client 构造：
   hook 每次都冷，daemon 只有第一次冷。差值已被实测夹住 —— `B-fail` 簇 802–808ms 对 800ms 上限，
   说明冷 import + 构造**通常只有 2–8ms**。相对 800→1300 的量级可忽略，**但两者不等价**。
2. **一条 948ms 的成功样本仍未解释。** 它高于 800ms 超时却成功了。
   假说是"冷 import 约 150ms + 请求 798ms 压线"，**未验证**。单点，不用于任何结论。
3. **探针文本 ≤500 字符，而 hook 把 prompt 截到 2000。** 实测记忆内容
   （n=5841）平均 290、最长 500，所以 2000 那条截断规则对记忆文本完全不生效。
   **更要紧的是：真实 prompt 的长度分布至今无记录**，因此三个取样方案
   （真实记忆文本 / 固定合成 / 随机长度合成）**没有一个能被验证**贴近真实负载。
   `prompt_chars` 落地几天后才能回过头校准取样长度。**在那之前，不要声称探针分布代表 hook 负载。**

## 九、成功判据

1. 探针连续运行 ≥3 天且 `enabled:true`，`embed-latency-probe.jsonl` 累积 ≥300 个样本。
2. 能回答 §一 那个问题：**把超时抬到 ~1300ms，那批超时里能捞回几次**（即样本中 800–1360ms 区间的占比）。
3. `timed_out_at_probe_limit` 的比例被报告出来 —— 它是分布尾部有多长的直接读数。
4. 定值后，用同一把尺子复测 `B-fail` 占比确实下降。

> **不作为判据的**：分位数对比。v0.14 已坐实它不可作判据，本文档不复活它。
